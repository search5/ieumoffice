# 0117 — WebDAV 서버를 여러 개 연결해 파일을 열고 저장한다

## 맥락

Google 드라이브(결정 0033, 0085) 말고 WebDAV 서버(Nextcloud, 시놀로지·QNAP NAS, 회사 파일 서버 등)의 파일도 이 앱에서 열고 고치고 싶다는 요청이 있었다(2026-11-09). 사용자는 범위를 "열기 + 저장"으로 정했고, AI가 WebDAV 파일을 찾아 읽는 기능은 나중에 붙일 수 있게 설계만 열어 두라고 했다. 인증은 Basic·Digest와 앱 비밀번호, 서버는 여러 개다.

Drive와 다른 점:

- 앱이 등록한 클라이언트도, 검증도, 브라우저 로그인도 없다. 사용자가 자기 서버 주소와 계정을 직접 적는다. 그래서 빌드 환경변수 없이 모든 빌드에서 쓸 수 있다.
- 서버 주소는 사용자가 정한 곳이다. 사설 IP·`localhost`도 허용한다(집 NAS). 대신 평문 HTTP는 사용자가 위험을 확인해야 연결된다.
- Google Workspace API 정책의 AI 학습 금지는 걸리지 않는다. 그래서 학습 설정 확인(`driveTrainingAck`)과 무료 연결 거절은 이번에 넣지 않았다. AI 읽기를 붙일 때 다시 정한다(아래).

## 결정

**패키지.** `packages/webdav`(`@genoffice/webdav`)에 순수 클라이언트를 둔다. Electron에 의존하지 않는다. 의존성은 늘리지 않는다(XML은 작은 해석기, Digest는 `node:crypto`).

**인증.** Basic과 Digest(MD5·SHA-256, `qop=auth`). 서버가 둘 다 내놓으면 Digest를 쓴다. 처음 호출은 로그인 정보 없이 보내고, 401의 `WWW-Authenticate`로 방식을 알아낸 뒤 그 서버에 대한 호출은 미리 서명한다. 사용자 이름을 비우면 로그인 없는 서버다. OAuth는 하지 않는다(서비스마다 흐름이 달라 작업이 크다). Nextcloud·Google 계정 등은 앱 비밀번호로 쓴다.

**비밀번호 보관.** `safeStorage`(Windows DPAPI, macOS 키체인)로 암호화해 데이터 폴더의 `webdav-servers.json`에 둔다. 암호화를 쓸 수 없는 PC(키링 없는 Linux 포함)에서는 서버 항목만 저장하고 비밀번호는 메모리에만 둔다. 앱을 다시 켜면 설정에서 다시 입력하게 한다. 화면 쪽 창은 비밀번호를 돌려받지 못한다(서버 목록에는 `hasPassword`만 있다).

**연결 확인.** 서버를 추가할 때 `PROPFIND`(Depth 0)로 로그인과 폴더를 확인하고, 통과해야 저장한다. 서버는 10개까지다.

**평문 HTTP.** 주소가 `http://`이면 "암호 없이 네트워크를 지난다"는 경고와 확인 체크가 있어야 연결된다. 뒷단도 같은 값(`allowInsecure`)을 다시 본다.

**열기.** 홈의 "WebDAV"에서 서버를 고르고 폴더를 따라 들어가 파일을 연다. 고른 파일은 데이터 폴더의 `webdav-cache`에 내려받아 보통 파일처럼 탭으로 연다. 열 수 있는 형식은 Drive와 같다(`OPENABLE_EXTENSIONS`). 이미 받은 사본은 서버의 ETag(없으면 수정 시각)가 같거나, 로컬에 아직 올리지 못한 수정이 있거나, 탭에 열려 있으면 다시 받지 않는다.

**저장.** 사본을 저장하면 감시기가 알아채 같은 서버 파일에 올린다. 올릴 때 사본을 받았을 때의 상태를 조건으로 건다(강한 ETag는 `If-Match`, 약한 ETag·태그 없음은 올리기 직전에 상태를 보고 비교). 서버가 그동안 바뀌었거나 파일이 사라졌거나 쓸 권한이 없으면 덮어쓰지 않고 사람에게 묻는다: 덮어쓰기(바뀐 경우에만), 서버에 사본으로 저장(`이름 (사본).확장자`, 이미 있으면 번호), 이 PC에만 저장. 올리기 실패(네트워크, 서버 과부하, 잠김)는 사본을 PC에 두고 30초·2분·10분 뒤에 다시 시도하며, 마지막에도 안 되면 알린다. 서버를 다시 연결하거나 비밀번호를 다시 넣으면 기다리던 저장이 올라간다. 앱을 다시 켜도 올리지 못한 저장은 이어서 시도한다.

**AI.** 처음 범위에는 AI 도구가 없었고, 같은 날 AI 읽기를 결정 0118로 더했다. 터미널 명령어, MCP, 에이전트 모드에는 WebDAV를 주지 않는다.

## AI 읽기를 붙일 때 정할 것 (결정 0118이 정했다)

- 자리: `webdav-files.ts` 옆에 `webdav-ai.ts`(검색은 `PROPFIND` 목록 + 이름 필터, 읽기는 `download` → `parseFileToText`)와 `packages/agent-core`의 `drive-skill.ts`를 본뜬 도구를 둔다. `parseFileToText`를 거치므로 가리기가 다른 파일 읽기와 똑같이 적용된다(결정 0016).
- 정해야 할 것: ① 학습 설정 확인을 Drive와 같은 체크로 묶을지 따로 둘지(Google 정책은 걸리지 않지만, 사용자의 서버 데이터가 AI 제공자로 간다는 점은 같다). ② 무료 연결(`isFreeAi`)에는 주지 않는 규칙을 이어받을지. ③ 서버별 "AI가 읽기" 스위치. ④ 한 번의 AI 실행에서 읽은 뒤 바깥으로 내보내는 도구(웹 검색, 주소로 그림 가져오기)를 막는 `setAiRunGuard` 규칙(결정 0033)을 똑같이 건다.
- 이번에 미리 해 둔 것: 서버 단위의 `id`와 연결한 폴더 기준 상대 경로, 서버 목록·목록 조회·상태 조회가 AI와 상관없이 쓰이는 형태.

## 택하지 않은 것

- **`DriveFiles`를 공통 클래스로 합쳐 두 서비스가 쓴다.** 같은 모양이지만 Drive는 Google 문서 내보내기·바로가기·`headRevisionId`·선택 창을 안고 있고, 이번 일이 Drive의 동작을 바꿀 위험을 만들 이유가 없다. 원본과의 차이를 작게 유지하는 규칙(`docs/standards.md`)에 따라 Drive 코드는 건드리지 않았다. 복사한 부분은 감시기, 색인, 재시도, 질문 흐름이다. 세 번째 저장소가 생기면 그때 합친다.
- **WebDAV 폴더를 PC에 마운트하거나 `Z:` 드라이브로 잡게 한다.** 운영체제마다 방법이 달라 앱이 맡을 수 없고, 저장 충돌을 앱이 볼 수 없다.
- **`webdav` npm 패키지를 쓴다.** 의존성과 라이선스 검사가 늘고, `electron.net` 대신 Node 네트워크를 타서 프록시·인증서 설정이 달라진다. 이 앱은 Drive와 같은 `net.fetch`를 쓴다.
- **OAuth(Nextcloud Login Flow 포함).** 서버마다 흐름이 달라 이번 범위 밖이다. 앱 비밀번호로 충분하다.
- **인증서 검증을 끄는 옵션.** 자체 서명 인증서를 쓰는 NAS가 많지만, 끄는 스위치는 비밀번호를 가로챌 길이 된다. 필요하면 시스템 인증서 저장소에 그 인증서를 넣게 안내한다(`docs/tracking/findings.md`에 적었다).

## 결과

- 사용자는 설정 → 연동에서 WebDAV 서버를 더하고, 홈의 WebDAV에서 열고, 저장하면 서버에 올라간다.
- 새 전송 경로가 하나 생긴다: 앱 ↔ 사용자가 적은 WebDAV 서버(목록, 내려받기, 올리기, 로그인). `PRIVACY.md`에 적었다. 앱이 정한 제3자 서버는 없다.
- 새 PC 쪽 파일: `webdav-servers.json`(서버 목록, 비밀번호는 암호화), `webdav-cache/`(열어 본 사본과 `index.json`). 사본은 30일 안 열지 않고 올리지 못한 수정도 없으면 지운다.
- 남은 것: 실제 서버(Nextcloud, 시놀로지 Digest, 자체 서명 인증서) 사람 확인. 단위 테스트는 가짜 서버로 로직만 확인했다. `docs/tracking/status.md`에 적었다.
